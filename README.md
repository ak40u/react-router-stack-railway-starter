# React Router stack for Railway

Accounts, sessions and per-user data on Postgres — React Router 8, React 19,
Prisma 7.

## Why this exists

The Remix Indie Stack template on Railway builds from a repository last touched
in **April 2022**, and its `package.json` says:

```json
"remix": "*",
"@remix-run/react": "*",
"react": "^17.0.2",
"@prisma/client": "^3.11.0"
```

`"*"` is not a version. It resolves to whatever npm publishes today, against
application code written for Remix 1.x — the install and the code cannot agree,
and **no deployment of it succeeds**: the template reports 0% health.

Remix has since merged into React Router, which is now at 8. This is the same
idea rebuilt on it: the thing the Indie Stack was actually for — a working
account system with per-user data — on versions that exist.

## What you get

Sign up, log in, write notes, delete them. Your notes; not anyone else's.

| File | Why it exists |
|------|---------------|
| `app/lib/auth.server.ts` | Password hashing, cookie sessions, route guards |
| `app/lib/prisma.server.ts` | Prisma client through a driver adapter, one per process |
| `app/routes/notes.tsx` | The data, scoped to the signed-in user |
| `prisma/schema.prisma` | `User` and `Note`, cascade on delete |
| `railway.json` | Migrations pre-deploy, health check on `/healthz` |

## Five decisions worth understanding

- **Login takes the same time whether or not the account exists.** A missing user
  is compared against a throwaway hash rather than returning early. Skipping the
  hash is measurably faster, and that difference tells an attacker which emails
  are registered.
- **Ownership is part of the query.** Deleting a note filters on `userId` as well
  as `id`, so guessing someone else's id changes nothing. A check that the caller
  is trusted to have made is not a check.
- **Logging out is a POST.** A GET would let any page on the internet sign your
  users out with an `<img src="/logout">`.
- **Migrations run pre-deploy, not at build.** The build container has no
  database. `prisma generate` does run at build, because generated client code has
  to be in the image — they are different containers, and files written in the
  second do not survive.
- **The health check asks the database.** A process that is up but cannot reach
  Postgres is not serving anything.

## Run locally

```bash
npm ci
cp .env.example .env      # DATABASE_URL, and a long random SESSION_SECRET
npx prisma migrate dev
npm run dev               # http://localhost:5173
```

## Configuration

| Variable | Required | Purpose |
|----------|----------|---------|
| `DATABASE_URL` | yes | Postgres connection string — wired to the Postgres service |
| `SESSION_SECRET` | yes | Signs session cookies — generated by the template |
| `PORT` | no | Set by the platform |

Changing `SESSION_SECRET` signs everyone out. That is the point of it: it is the
lever you pull if you think a session has leaked.
